# Turning on the self-serve demo

The website's "Try it yourself" page gives a prospect a private, 7-day demo of Keystone. This page lists what has to
exist in Azure and which settings to fill in. Nothing here is created automatically.

## How it fits together

```
KS-Website /try  --POST /api/public/demo/signup-->  KS-Ops  --magic link email-->  prospect
prospect clicks link -> KS-Portal /demo#d=..&t=..  --POST /api/public/demo/open-->  KS-Ops
KS-Ops  --POST /api/demo/ops/sessions (X-KS-Ops-Key)-->  demo KS-server (DEMO_MODE=true)  -> staff token
KS-Portal /demo  <--staff token-->  demo KS-server /api/demo/staff/*      (walkthrough, documents, call, lenders)
phone: KS-Client /demo/<code>  <--client token-->  demo KS-server /api/demo/client/*   (uploads, assistant)
demo KS-server  --progress events + lender package (X-KS-Ops-Key)-->  KS-Ops  --> emails: prospect + sales
KS-Ops job (every 10 min): idle/expired "didn't finish" email to sales; after 7 days wipe on the server and here
```

- **One shared demo server** for every prospect: a normal KS-server build with `DEMO_MODE=true`. In that mode only
  `/api/demo/*` and health answer; every other route returns 404, and no background worker runs (no texts, calls,
  emails, Office/Google sync or ad conversions can happen). The server itself sends no email at all.
- **Each prospect is a session** with its own copy of the sample file (business, owner, application, financials),
  seeded from a fixture when the session is made. Fictional lenders only. Every query filters on the session id, and
  the id comes only from the signed demo token, so one prospect can never see another's data (tested).
- **KS-Ops owns** the sign-up, the magic link, opening the session on the demo server, progress tracking and the two
  emails (the lender package to the prospect, the summaries to `KS_SALES_EMAIL`).
- Sessions last `DEMO_SESSION_DAYS` (7). After that KS-Ops wipes the session on the server and drops its events and
  package; the lead (name, email, company and a digest of what they did) stays in KS-Ops for sales. The demo server
  also wipes anything expired more than an hour ago on its own.

## Azure resources

Put them next to the dev copy (resource group `ks-dev`) so the existing deploy service principal can reach them.

| What | Suggested name | Notes |
| --- | --- | --- |
| Web app for the demo KS-server | `ks-demo-server` | Linux, Node 22, on the existing `ks-dev` App Service plan (B1 is enough). Startup command `node dist/index.js`. HTTPS only, Always On. |
| Database | `ks_demo` on the dev Postgres flexible server | A separate **database** on the same server is fine (`CREATE DATABASE ks_demo;`). It must not be the dev database. The `vector` extension must be allow-listed on the server (it already is for dev). Add the demo web app's outbound IPs to the server firewall. |

No new Static Web Apps are needed: the demo pages are routes in the existing KS-Portal (`/demo`) and KS-Client
(`/demo/<code>`) web apps. (A separate KS-Portal Static Web App for the demo works too; then use its address below.)

### Seeding

Nothing to seed by hand. On first start the server loads the schema baseline into the empty `ks_demo` database and
runs the newer migrations (including `2026_10_24_ks_v10_demo.sql`). Each prospect's sample file is created from the
fixture (KS-server `src/demo/fixture.ts`) when KS-Ops opens their session. The sample PDFs are generated by the server
(`src/demo/samples.ts`) - the same bytes on every instance.

## Settings

### Demo KS-server (`ks-demo-server` app settings)

| Setting | Value |
| --- | --- |
| `DEMO_MODE` | `true` |
| `NODE_ENV` | `production` |
| `DATABASE_URL` | `postgres://<user>:<password>@<dev pg host>:5432/ks_demo?sslmode=require` |
| `JWT_SECRET` | a new random value, 32+ characters (`openssl rand -hex 32`). Do **not** reuse the dev server's. |
| `KS_OPS_URL` | the KS-Ops base address, e.g. `https://ks-ops.azurewebsites.net` |
| `KS_OPS_KEY` | a new random value, 32+ characters - the **same** value as `KS_DEMO_OPS_KEY` in KS-Ops |
| `KS_DEMO_CLIENT_URL` | the KS-Client web app address that serves `/demo/<code>` (the QR code / short link), e.g. `https://wonderful-island-0b68ae310.5.azurestaticapps.net` |
| `CORS_ALLOWED_ORIGINS` | the KS-Portal and KS-Client web addresses, comma separated (no trailing slash) |
| `OPENAI_API_KEY` | optional. With it the borrower's assistant answers with the model (about the sample file only); without it, scripted answers. |
| `DEMO_ASSISTANT_MODEL` | optional, default `gpt-4o-mini` |
| `DEMO_ASSISTANT_LIMIT` | optional, questions per session, default 12 |
| `DEMO_SESSION_DAYS` | optional, default 7 (keep it equal to KS-Ops') |

Leave every Twilio, Microsoft Graph, SendGrid, Google, SignNow and Azure Storage setting **unset** on the demo
server. The demo needs none of them, and leaving them empty is a second guarantee that nothing real can go out.

Deploy: in the KS-server repo set the GitHub **variable** `DEMO_WEBAPP_NAME=ks-demo-server`. The existing deploy
workflow then ships the same build to the demo web app after it deploys the dev server.

### KS-Ops (app settings)

| Setting | Value |
| --- | --- |
| `KS_DEMO_SERVER_URL` | `https://ks-demo-server.azurewebsites.net` (the demo web app) |
| `KS_DEMO_OPS_KEY` | the same value as the demo server's `KS_OPS_KEY` (16+ characters; 32+ recommended) |
| `KS_DEMO_PORTAL_URL` | the KS-Portal web address; the magic link opens `{KS_DEMO_PORTAL_URL}/demo#d=..&t=..`. It is also allowed by CORS on `/api/public/demo/*`. |
| `PUBLIC_SITE_URL` | already set (the website); the sign-up form posts from there |
| `KS_SALES_EMAIL` | where the sales notes go (default `keystone@boreal.financial`) |
| `MS_GRAPH_*` or `SENDGRID_*` | already needed for KS-Ops email; without one, demo emails are only logged |
| `DEMO_SMS_ENABLED` | `true` texts the demo link as well as emailing it. **Off by default**: the link is emailed only, and the mobile number is kept so sales can call |
| `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `KS_SMS_FROM` (or `TWILIO_MESSAGING_SERVICE_SID`) | with `DEMO_SMS_ENABLED=true`, texts the demo link to the mobile number given on the sign-up form (Canadian/US numbers) |
| `TURNSTILE_SECRET` | optional; when set, the demo sign-up requires the Turnstile check |
| `DEMO_SESSION_DAYS` | optional, default 7 |
| `DEMO_IDLE_HOURS` | optional, default 24 - when the "started but didn't finish" note goes to sales |
| `DEMO_MAX_ACTIVE` | optional, default 100 demos open at once |
| `DEMO_PER_EMAIL` | optional, default 3 demos per email address in 30 days |
| `DEMO_PER_IP_DAY` | optional, default 5 sign-ups per IP address per day |

Without `KS_DEMO_SERVER_URL`, `KS_DEMO_OPS_KEY` and `KS_DEMO_PORTAL_URL` the demo endpoints answer 503 and the website
shows "not available right now".

### KS-Portal (GitHub variables on the repo)

| Variable | Value |
| --- | --- |
| `VITE_KS_OPS_URL` | the KS-Ops base address |
| `VITE_DEMO_SERVER_URL` | the demo server address |

The deploy workflow writes them into the build and adds both addresses to the page's Content-Security-Policy
(`connect-src`), so the `/demo` page can reach them. Nothing else in the portal changes.

### KS-Client (GitHub variable on the repo)

| Variable | Value |
| --- | --- |
| `VITE_DEMO_SERVER_URL` | the demo server address |

The build adds it to the Content-Security-Policy `connect-src`. The borrower page is `/demo/<code>` (also `/d/<code>`).

### KS-Website (build setting)

| Variable | Value |
| --- | --- |
| `VITE_OPS_URL` | already set for sign-up; the "Try it yourself" page posts to `{VITE_OPS_URL}/api/public/demo/signup` |
| `VITE_TURNSTILE_SITE_KEY` | optional, the same Turnstile widget as sign-up |

## Checking it works

1. `GET https://ks-demo-server.azurewebsites.net/api/health` answers 200, and
   `GET https://ks-demo-server.azurewebsites.net/api/applications` answers 404 `not_available_in_demo`.
2. Sign up on the website's Try it yourself page with your own email. The magic link arrives.
3. Open it on a computer: the portal greets you by name and starts the walkthrough. Scan the QR code with a phone and
   upload the sample documents; they appear in the portal within a few seconds. The September statement is flagged red.
4. Finish the walkthrough. You receive the lender package PDF; `KS_SALES_EMAIL` receives the summary.
5. Start a second demo with another address and leave it: 24 hours later sales gets the "didn't finish" note.
